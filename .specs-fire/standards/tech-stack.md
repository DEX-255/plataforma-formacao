## Overview

Plataforma web responsiva, uma base servindo o site público e o app interno.
Escala esperada: ~50 participantes, ~10 mentores, ~15 encontros, ~3.000 registros de
feedback por edição. A stack se justifica por **RLS e login Google**, não por volume.

## Núcleo

| Camada | Escolha |
|---|---|
| Framework | Next.js (App Router) + TypeScript |
| Estilo | Tailwind, com os tokens de `specs/05-design-system.md` |
| Auth + banco | Supabase — Google OAuth + Postgres + RLS |
| Hospedagem | Vercel |
| Gráficos | SVG à mão, sem biblioteca |
| Documento final | HTML + CSS de impressão, PDF por Chrome headless |

## A decisão que não se reabre

**Next.js, e não React puro servido estático.** Sem servidor de aplicação, a política do
banco deixa de ser a segunda barreira entre o participante e a nota e passa a ser a
**única**. Com renderização no servidor, a tela com dado sensível é montada antes de
sair, e o que não é enviado não vaza — a RLS continua valendo por baixo como
redundância. Para `RN-03`, essa redundância é o produto.

O raciocínio completo está em `specs/06`, seção *Por que Next.js e não React puro*. A
troca chegou a ser feita e foi revertida; o histórico está em `pendencias.md`.

## Restrições que a stack precisa respeitar

- **Orçamento de JavaScript: < 120 KB comprimido por rota.** É orçamento, não
  estimativa. Medir a cada entrega.
- **Fontes hospedadas junto** (`D-05`), só os pesos usados, `font-display: swap`. Cinco
  famílias vindas do Google Fonts custam caro no 4G do corredor do INF.
- **Sem biblioteca de gráfico.** Três linhas, cinco pontos.
- **Migrações versionadas** em `supabase/migrations` (`D-06`). Mudança de esquema é
  arquivo revisável, nunca clique no painel.
